## 1. 一句话结论

这次跑通了一条适合 **UI 叙事、文字 MV、拟人 SVG 角色** 的生产线：

**参考片拆解 → 确定性网页时间轴 → Playwright 逐帧截图 → FFmpeg 编码混音 → 关键帧与成片双重 QC → 微信媒体交付。**

它没有调用视频生成 API，也没有把原片抽帧贴回画面。最终版本重新绘制了全部视觉内容，但仍沿用原片音乐和人声，方便对照节奏。

因此，本次完成的是 **画面复刻 + 原音轨对照版**，不是“原创音乐、原创配音全部重做”的完整原创版。

## 2. 调查结论与验收边界

原文把相关作品称为“代码动画”，并说明画面、音乐和配音由 AI 制作。[1]

从原文提取到的 Claude 参考视频参数为：

| 项目 | 参考片 |
|---|---:|
| 时长 | 约 180.37 秒 |
| 分辨率 | 854×480 |
| 帧率 | 30 fps |
| 内容 | 登录页、“记住我”、封号、申诉、自动回复与光标自述 |

只有 MP4，没有作者源码，所以只能确认其视觉构件，**不能据此断言原作者用了原生 JS、GSAP 或某个特定框架**。

适合网页复刻的依据是画面本身：

- 登录表单、聊天气泡、浏览器窗口等 UI 构件；
- 米白半调纸张、深蓝夜景、炭黑自动回复等主题切换；
- 可拆成 SVG 路径的橙色拟人光标；
- 大字排版、计数器、歌词和场景时间轴。

## 4. 思路拆分

### 4.1 先取得参考片，不凭文章想象画面

常规文章抓取受阻后，改从可联网的远程环境取回文章 HTML，再从视频标签和地址中定位真实 MP4。

随后对参考片做三类拆解：

1. **时间结构**：时长、镜头起止、歌词和剧情节点。
2. **视觉系统**：配色、字体层级、卡片、角色、背景与转场。
3. **声音结构**：音乐、人声和歌词时间轴。

转写使用 faster-whisper，画面文字使用 Tesseract OCR，接触表和代表帧用于人工与视觉模型审查。视觉模型只参与分析，不生成最终画面。

### 4.2 把 3 分钟拆成“章节—场景—构件”

没有直接写 180 秒的大段动画，而是先拆章节，再落到 31 个场景：

| 时间 | 叙事任务 | 主要视觉 |
|---|---|---|
| 0–19.57 秒 | 聊天开场与标题 | 聊天气泡、登录提示、主标题 |
| 19.57–48.26 秒 | 光标自我介绍与共同工作 | 输入框、365 天、03:00、17 版需求 |
| 48.26–80.58 秒 | “记住我”第一次情绪抬升 | 便签、计数、大字、阳光背景 |
| 80.58–111.24 秒 | 封号、申诉与自动回复 | 浏览器、放大镜、申诉信、炭黑卡片 |
| 111.24–138.02 秒 | 三百万次闪烁与未说完的话 | 夜景、输入框、计数器、绷带角色 |
| 138.02–166.54 秒 | 回到登录页与情绪回应 | 登录卡、问句、阳光段、角色群像 |
| 166.54–180.37 秒 | “换我记住你”收尾 | 登录卡、角色、收束文案、淡出 |

每个场景再复用少量构件：`login()`、`browser()`、`mascot()`、`check()`、`title()`。这样能保持角色和 UI 一致，不必逐镜重新设计。

### 4.3 用确定性时间轴代替实时录屏

核心接口是：

```js
window.renderFrame = function (t) {
  // 由绝对时间 t 计算场景、位置、透明度、计数器和歌词
};
```

场景数据形如：

```js
{ s, e, theme, html, update }
```

- `s / e`：起止秒数；
- `theme`：暖纸、桃色、阳光、夜景、炭黑等主题；
- `html`：场景构件；
- `update`：该场景内随时间变化的属性。

这样设计的价值不是“代码更漂亮”，而是让任意帧都可独立重建。拖动预览、导出单帧、分段渲染和全片渲染走的是同一个函数。

实时 CSS Animation、`setTimeout` 和依赖前序帧的状态不适合这条管线，因为直接跳到 `t=120` 时无法保证与顺序播放到 120 秒一致。

### 4.4 画面与声音分开处理

- 画面：HTML / CSS / JS / SVG 全部重绘。
- 对照音轨：从参考片提取，保留音乐和人声。
- 歌词：维护 `[start, end, text, emphasis]` 时间轴。
- 合成：FFmpeg 按渲染起点对音轨使用 `-ss`，按片段长度使用 `-t`。

第一版沿用原音轨是对的：它能直接暴露节奏和镜头边界是否接近参考片。但若目标是可公开发布的原创版本，下一步应更换音乐与人声，并重新校准歌词和口型。

### 4.5 先审关键帧，再烧完整时间

完整渲染前做了：

- 全片定时抽帧和接触表；
- 31 个场景的代表帧检查；
- 15 秒真实编码样片；
- 24 个指定时间点的集中审查；
- 问题修复后的四帧复查。

视觉审查实际发现了 30 秒角色出框、90 秒角色被浏览器裁切、120 秒角色遮挡“在吗？”等问题。发现后停止全片渲染，先修画面再重跑，避免把已知错误编码进最终版。

### 4.6 成片验证与交付是两道独立验收

画面文件生成成功，不等于视频可交付；视频可交付，也不等于用户已收到。

本次验证分三层：

1. **源画面**：浏览器无 JS 错误，关键帧无遮挡、出框和小字问题。
2. **成片**：检查时长、分辨率、帧率、音轨，完整解码，再从 MP4 抽帧。
3. **投递**：另出 4.8 MB 微信版，通过一次性 cron 任务重发媒体。

初版 24.5 MB 文件未被用户收到。日志中能看到当日多次 iLink 文本限频，但不能仅凭这些日志断言“媒体失败就是文件太大”。可复用的原则是：**不要把回复中写了 `MEDIA:` 当成送达证明；要查投递日志，并以用户实际收到为最终确认。**

## 6. 关键问题与修复

| 问题 | 根因 | 修复或教训 |
|---|---|---|
| 文章和视频不好抓 | 常规访问受限 | 换可用网络环境取得 HTML，再定位真实媒体地址 |
| 初稿偏普通 UI 展示 | 对参考片角色和纸张风格抓得不够 | 回到抽帧，确立拟人光标、半调纸张和夜景三条视觉主线 |
| 任意时间 seek 可能不一致 | 实时动画依赖播放状态 | 所有视觉状态改由 `renderFrame(t)` 计算 |
| 30 秒右侧角色出框 | 大勾选区缩放过大，变换原点偏左 | 缩放改为 1.45，原点改为 center |
| 90 秒角色被裁切 | 角色放在浏览器内容区底边之外 | 改为 tiny 角色并移入内容区，说明文字移到右侧 |
| 120 秒角色挡住“在吗？” | 角色与输入框安全区重叠 | 横坐标从 350 改为 200 |
| 小字与歌词安全区不足 | 只按设计稿观感判断 | 增大标签和输入字号，歌词上移，结尾说明上移并放大 |
| 渲染循环与成片差一帧 | `-shortest` 在尾部截断 | 当前不影响验收；后续应显式计算帧边界并断言输出帧数 |
| 首版与后续源码快照不清 | 多轮迭代覆盖同一路径 | 每版用独立目录、Git tag 或源码归档，不让成片与源码版本脱节 |
| 用户未收到附件 | 媒体投递与会话文本投递不是一回事 | 压缩交付副本、查日志、重发并等用户确认，不凭工具返回值报成功 |

## 7. 有没有更好的方案

### 7.1 对这支片：不必推翻原生方案，优先补工程化

原生 HTML / SVG 已经适合这支片。真正的瓶颈不是渲染速度，而是：

- 场景 HTML 大量内联，修改牵一发动全身；
- 绝对像素定位较多，角色遮挡只能靠目检发现；
- 缺少自动化视觉回归；
- 音频、场景和歌词数据没有彻底分离；
- 单浏览器顺序渲染，尚未利用确定性时间轴做并行分段。

**推荐保留渲染管线，重构创作层。**

### 7.2 方案对比

| 方案 | 更适合的片型 | 优点 | 代价或限制 | 本项目结论 |
|---|---|---|---|---|
| 原生 HTML / CSS / JS / SVG，当前方案 | 高度定制的 UI 故事、文字 MV | 自由度高，依赖少，已完整实测 | 手动布局和维护成本高 | 继续用于本片 |
| 原生方案工程化 | 同类定制 MV 的后续版本 | 保留现有资产，逐步解决测试、布局和并行问题 | 需要自己搭场景规范与 QC | **本片下版首选** |
| Remotion | 系列化视频、React 团队、参数化模板 | React 组件、Composition 元数据、按帧模型和正式渲染 API 完整 [3][4] | 需要迁移到 React / Remotion 项目结构 | 长期系列制作优先评估 |
| Motion Canvas | 程序化运动图形、教学动画 | TypeScript、generator 编排、实时预览；场景和动画流程表达清晰 [5] | 与现有 DOM UI 资产不是一个创作模型 | 新运动图形项目可选 |
| answer-me-with-html | 3–6 幕的技术讲解、图解和短片 | Markdown 草稿即可生成页面和播放器，少写布局代码 [2] | 不适合直接承载本片 31 幕、定制角色和精确 MV 节奏 | 做短讲解更快，不做本片主方案 |

Remotion、Motion Canvas 和 answer-me-with-html 是本节的技术选型建议，**本次没有为它们重新搭建同一支片并做速度或质量基准测试**。因此不把“更快”或“效果更好”写成已实测结论。

## 8. 推荐的下版架构

如果继续原生方案，建议改成数据驱动，但保留 `renderFrame(t)`：

```text
src/
  components/
    mascot.js
    login-card.js
    browser-window.js
    typography.js
  scenes/
    00-opening.js
    01-cursor-intro.js
    ...
  data/
    remember-me.scene.json
    remember-me.lyrics.json
  lib/
    easing.js
    layout.js
    timeline.js
  render/
    worker.mjs
    concat.mjs
  qc/
    capture-boundaries.mjs
    assert-layout.mjs
    verify-video.mjs
```

优先做五项：

1. **场景数据外置**：起止时间、主题、组件和 props 放进 JSON；歌词单独维护。
2. **安全区布局**：为角色、输入框、歌词和卡片定义允许区域，减少散落的绝对坐标。
3. **边界自动测试**：每个场景检查 `start-ε / start / mid / end-ε`，并随机重复 seek 比较结果。
4. **DOM 几何断言**：检测超舞台、文字溢出、角色与关键文字相交；允许出血的元素显式加白名单。
5. **并行分段渲染**：多个浏览器 worker 按整数帧边界渲染无音轨分段，最后 concat 并统一混音一次。

并行化之所以可行，是因为任意帧只依赖 `t`，不依赖前一个 worker 的状态。渲染提速后，关键帧 QC 仍不能省。

## 9. 如果目标是“完整原创版”

建议把顺序反过来：

1. 先确定原创歌词、旁白和音乐；
2. 生成或录制人声，确认音色和语速；
3. 从最终音频得到歌词、重音和场景时间点；
4. 再按音频制作画面；
5. 最后做响度、字幕、版权与发布检查。

本次“先复刻画面、沿用原音轨”适合验证技术路线，但不适合作为原创音频工作流的模板。
