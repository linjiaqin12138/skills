# 复杂度阶梯：按需增长

架构复杂度的默认方向是**少**。每一层、每个抽象都是**有代价**的：更多的文件、更长的调用链、更难定位错误、更容易写出无意义样板。只有当具体需求出现时，才付这个代价。

反模式：照着架构图一次性铺满 Protocol / Service / UseCase / Provider / Repository / Port / Adapter / UnitOfWork，然后发现三个空壳层和一个没人调用的 Port。

## 阶梯

| 级 | 结构 | 引入条件（**不满足就不许加**） | 不加会怎样 |
|---|---|---|---|
| 0 | 单文件 / 单脚本 | 一次性、不可复用、无外部依赖、无持久化 | —— |
| 1 | + Service | 同一段逻辑出现**第二处**调用；或逻辑已超出"一个函数说清"的范围 | 复制粘贴，逻辑分叉 |
| 2 | + UseCase | Service 里出现**第二条独立工作流**；或某段逻辑需要独立的事务 / 重试 / 错误码策略 | 一个 Service 方法里塞多件事，改一处崩一片 |
| 3 | + Provider | 出现第二个外部 API/SDK；或测试需要一个稳定的 patch 边界 | 传输细节散进业务代码，测试必须联网 |
| 4 | + Repository | 出现真实持久化需求 | SQL/ORM 调用混进业务层，无法测事务与约束 |
| 5 | + Port + Adapter | 同一能力出现**第二种实现**；或有确凿的替换/替身需求 | —— （大多数项目永远不需要这一级） |
| 6 | + UnitOfWork | 重复的事务生命周期代码**已经出现**，且 UnitOfWork 能真实消除它 | —— |
| 7 | + 组合根 / 资源生命周期 | 长驻进程（服务、消费者、调度器）需要共享资源与关闭流程 | —— |
| 8 | + 请求上下文 / 可观测性 | 出现用户/租户/trace/幂等键等多租户或分布式追踪需求 | —— |

## 每一级的判定问题

升一级之前，先回答这三个问题。**答不出"是"，就不升。**

1. **触发条件是什么？** 必须能写成一句可验证的话，例如"现在有第二个外部 API 了"、"Service 里已经有两条独立工作流了"。写不出来的触发条件，说明这是"觉得应该这样"，不是需求。
2. **不升会痛吗？** 说得出具体的痛点（测试跑不起来、改动牵连一片、无法保证事务），而不是"不够规范"。
3. **升级后怎么证明有效？** 例如"Service 层现在能独立测试，不需要启动 HTTP 服务"。升完要能指出收益。

## 反向：允许降级

层级不是单向棘轮。以下情况应当**合并回去**：

| 情况 | 动作 |
|---|---|
| UseCase 只有一个调用方，且没有独立的事务/重试/错误码策略 | 收回 Service，或与其他 UseCase 合并 |
| Service 只有一个方法，且那个方法只是转发 | 考虑让 Protocol 直接调用（此时 Service 层还没必要存在） |
| Provider 只有一个调用方，且只是包了一层薄 HTTP | 可以内联，但保留独立函数边界（为了可 patch） |
| 出现了空的 Port / 空的 Adapter / 没人调用的 `run()` 通用入口 | 删除 |
| tests 里出现"为了对应某一层"而写的平行测试套件 | 删除，断言合并到真正的归属层 |

**空壳层比没有层更糟**：它制造"这里应该有点什么"的错觉，让后来的人往里面塞逻辑。

## 每个可选抽象的"红线"

这些是最容易被提前引入的东西。写下明确的禁止条件：

### UseCase

- ❌ 一个 UseCase 里用 `action` 字段 / 大 `if-else` 分派多个独立操作
- ❌ 一个 UseCase 只是为了"看起来有层"而包住 Service 里的一行逻辑
- ✅ 一个 UseCase = 一个完整动作；多个独立动作 → 多个 UseCase + Service 上的多个语义化方法

### Provider

- ❌ 为了测试而引入 Provider 接口（抽象基类 + 实现类）
- ❌ 模块级全局 client / 全局缓存（会导致账号、凭据、沙箱模式互相串味，测试互相污染）
- ❌ Provider 里读配置、选账号、选择别的 Provider
- ❌ 在 Provider 里做分钟级 job 轮询 /「等任务完成」（那是 UseCase/Service 编排）
- ✅ 具体函数 + 显式参数；测试直接 patch 这个函数；提交/查状态/下载拆开

### Port / Adapter

- ❌ "接了第三方所以要抽象一层"
- ❌ Port 镜像整个第三方 SDK
- ✅ 直到出现第二种实现或确凿替换需求

### UnitOfWork

- ❌ 默认就上 UoW 包装
- ❌ 嵌套事务（子 UseCase 自己 commit）
- ✅ 默认直接用 ORM 的 session factory；重复的生命周期代码出现后再考虑

### Repository

- ❌ 每个 CRUD 都套一层"基类 + 泛型"
- ❌ 返回 Result / ServiceResult
- ✅ 具体函数，按领域能力命名（`create_order`、`query_orders`）

### 分层整体

- ❌ 为单协议项目（只有 CLI）硬造完整五层
- ❌ 把"领域模型"和"请求/响应 DTO"混为一谈
- ✅ 层级按实际接入面数量与外部依赖数量决定

## 组件归属判定：utils / UseCase / Engine

阶梯管的是**层级深度**；组件归属是另一个问题。拿不准时用这张表：

| 判据 | 结论 |
|---|---|
| 懂本项目的领域词汇（symbol、order、position…） | UseCase（或 Service） |
| 无状态、无副作用、通用、与领域无关 | `utils/`（纯工具） |
| 无领域词、显式参数、本地 IO、机制码 Result | `utils/<capability>`（机制型效应工具；**可单调用方就独立**，便于发现） |
| 无领域知识，但有状态，且大到能自己管生命周期 | **Engine**（`src/engines/<name>/`） |
| 是无状态第三方调用 | Provider |
| 是数据库读写 | Repository |

**机制型效应工具 vs 领域旁路函数**：语义已是稳定机制（如 `resolve_under_root`）→ 立刻进 `utils/fs` 一类目录，不要等第二个调用方，也不要藏在 Service 私有方法里。还夹着领域含义或边界未定 → 留在调用方旁边。

**引擎的识别标准（必须同时满足）**：

- 可以作为**独立 SDK 发布**——有自己的公开 API、版本和测试，脱离本仓库也成立
- **不含 domain knowledge**
- **不依赖核心领域模型**（自己的输入输出类型，由调用方转换）
- 可以依赖 `providers/`、`utils/` 等通用设施

引擎**永远不放 `utils/`**。utils 是按能力组织的小工具（纯或机制型）；引擎是有自己模型、配置、生命周期和失败模式的子系统。把引擎塞进 utils，等于把一整个系统伪装成工具函数目录。

**引擎的降级条件**：如果它只有一个调用方、没有独立生命周期、也不打算独立发布，那它就不是引擎，应该收回 UseCase（或拆成 Provider + utils）。反过来，一个已经发布出去、被别的项目依赖的引擎，就**不能**再被塞回 UseCase。

## 新增一层时的登记

每次升级一级，在仓库里留下痕迹（ADR 或 README 一段）：

```text
日期：2026-11-09
从级别 2 升到级别 3（引入 Provider）
触发条件：接入了第二个外部 API（行情源），且现有测试必须联网才能跑
收益：Provider 层可被 patch，Service 测试可离线运行
后续升级触发条件（尚未满足）：当行情源出现第二种实现时，考虑引入 Port
```

**同时写下"下一个触发条件"**，这样后来的人知道当前层级不是随手搭的，也知道什么时候才该继续往上加。
