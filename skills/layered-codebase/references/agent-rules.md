# Agent 写码红线

目标：让 agent 的产出**可预测**——同样的需求，不同的 agent 写出来的结构应该一样；改代码时 review 的人不用重新判断"这东西该放哪"。

核心思路：**能用工具判定的，就不要交给 agent 判断力。**

## 1. 确定性 vs 建议性

| 类型 | 例子 | 落地方式 |
|---|---|---|
| 确定性（必须永远成立） | 禁止反向依赖、禁止新增顶层目录、必须通过 lint/type/test、禁止提交密钥 | 工具：linter 规则、类型检查、测试、CI、pre-commit、hook、deny 规则、权限规则 |
| 建议性（需要判断） | 命名是否贴切、抽象是否值得、错误码是否分类合理 | 文档 + review 清单 + ADR |

写文档时把规则归到正确的栏里。**"请务必不要新增顶层目录"写在文档里只是建议；放进 CI 检查才是约束。**

## 2. 必须先问再做的操作

- 新增/重命名**顶层目录**
- 引入新的**依赖**（含运行时依赖、构建工具、格式化器）
- 改变**公开接口**（对外暴露的方法、协议字段、错误码集合）
- 修改 **AGENTS.md 里的命令**、CI 配置、锁文件
- 大规模重命名/移动文件
- 删除或改写既有测试的断言

其余情况（新增文件、重构函数内部、加测试、改文档细节）直接做。

## 3. 变更规模

- 一次改动**只做一件事**。不把重构、格式化、依赖升级、命名调整混进来。
- 不顺手格式化全仓库、不顺手升级依赖、不顺手"优化"没碰到的代码。
- 触碰文件数控制在个位数量级；确实需要大面积改时，先说明方案再动手。
- **不重写**。代码难读不等于该推倒重来；旧代码里的每一处丑陋通常都对应一个真实踩过的坑。按需增量改造（`references/complexity-ladder.md`）。
- 保留已有的、正确的、虽然不喜欢的模式；新代码不要复制仓库里已知的坏模式，但也不要为了统一而顺手大改。

## 4. 分层红线（写码时反复自检）

- 业务逻辑不许出现在 Protocol 里（只解析、调用、渲染、映射）。
- Provider 不许读配置、不许选账号、不许调别的 Provider、不许持有全局 client。
- Repository 不许 commit、不许返回 Result、不许自己开事务。
- Service 不许写工作流、不许有通用 `run()`、不许做 UseCase 模型的校验。
- UseCase 不许把多个独立动作塞进一个（不许 `action` 分派）。
- `utils` 不许 import 任何应用层；不许建 `common.py` 式垃圾桶。
- **引擎（Engine）不许放进 `utils/`**，也不许写成 UseCase：引擎 = 无领域知识、可独立发布的子系统。引擎不许依赖 protocols/services/use_cases；只暴露一个门面。
- 引擎不许使用模块级全局 client；运行模式（dry-run/sandbox/live、live/synthetic/replay）必须是显式配置；影响结果的随机性必须是显式入参，不许改全局随机数种子。
- `models` 不许变成"所有数据类的回收站"。
- 任何层的代码都不许反向 import 上层。

## 5. 状态与副作用

- **禁止模块级可变全局**（全局 client、全局缓存、全局计数器）。需要共享时由 Service/组合根持有并显式传入。
- 禁止用"默认参数 + 全局单例"来让参数变可选——不同账号、凭据、沙箱模式会互相串味，测试也会互相污染。
- 凭据、token、账号选择不许硬编码或写死在仓库里（12-factor 的 Config 原则）。
- 固定的第三方端点写在 Provider 内部，不作为参数到处传。

## 6. 错误处理

- 业务可预期的失败返回 Result + 错误码，不靠抛异常做流程控制。
- `code` 是跨层契约；不许用异常类型名做分支条件。
- 不许拿 `unknown` 做分支条件；默认分支兜住它。
- 不许 catch `BaseException`、不许吞掉取消信号、不许静默吞异常（要么处理、要么转换、要么往上抛）。
- 原始异常只作内部诊断，不进外部响应。

## 7. 测试

- 遵守 `references/testing.md` 的归属表与 patch 策略。
- 新增行为要有测试；改行为要改对应归属层的测试，不要在别的层加一份重复的。
- 不许为了通过 CI 而删断言、跳过测试、加 `xfail` 掩盖问题（除非确实是已知缺陷并写明原因与跟踪方式）。

## 8. 提交与 PR

- 提交信息遵循 Conventional Commits：`<type>(<scope>): <description>`
  - `type`：`feat` / `fix` / `refactor` / `test` / `docs` / `build` / `chore` / `perf`
  - `scope`：**对应模块目录名**（如 `services`、`providers`、`protocols/cli`）
  - 破坏性变更加 `!` 并在正文写 `BREAKING CHANGE: ...`
- 一次提交一件事。
- PR 描述要能让人不看代码就明白：做了什么、为什么、怎么验证的（贴命令输出）、影响范围。
- PR 里不放顺手做的无关改动。

## 9. 决策记录

出现下列任一情况，**必须**写一条 ADR（`docs/adr/NNNN-<slug>.md`）：

- 引入新的依赖
- 引入新的抽象层 / 改变分层结构（对应复杂度阶梯升一级）
- 对外接口或协议变更
- 数据模型/数据库 schema 变更
- 改变了"重试/事务/错误分类"这类全局策略
- 放弃了某个已有方案（写清为什么放弃）

ADR 模板：Context（要解决什么、约束是什么）→ Decision（决定了什么）→ Consequences（好处、代价、后续触发条件）。

## 10. 文档

- `README.md`：给人看的，控制在能快速上手的长度。
- `AGENTS.md`：给 agent 看的，**只写它猜不到的东西**：装依赖、跑测试、跑检查、提交规范、目录约定。**不要**复述目录树里已经能看出来的结构（Anthropic 的 CLAUDE.md 指南：能读代码得到的就别写）。控制在 200 行以内。
- `docs/`：按 [Diátaxis](https://diataxis.fr/) 四象限分：tutorial（上手）/ how-to（做某事）/ reference（查某物）/ explanation（为什么）。一篇文档只属于一个象限。
- 文档与代码不一致时，**以代码为准并立刻修文档**；不要让文档描述旧行为。

## 11. 完成定义（Definition of Done）

改完代码，逐条确认；**有检查命令的必须真的跑过并把输出贴出来**：

- [ ] 分层落位正确：无反向依赖、无跨层 import、无空壳层
- [ ] 新增/变更的错误码有明确归属，并逐层显式映射
- [ ] 每个新行为有测试，且归属不重复
- [ ] lint / type check / test 全部通过（命令见 AGENTS.md）
- [ ] 没有新增依赖、没有新增顶层目录（除非明确批准并已记录）
- [ ] 没有引入模块级可变全局、没有硬编码凭据
- [ ] 提交信息符合 Conventional Commits，scope 对应模块
- [ ] 触发 ADR 条件的决策已写 ADR
- [ ] 文档与代码一致
- [ ] 最终回复里贴出了实际运行的命令与输出（不是"应该没问题"）

## 12. 自检提问（agent 在提交前问自己）

1. 这段代码属于哪一层？如果说不清，说明位置选错了。
2. 它的错误码属于哪一层？下游怎么映射？
3. 它的测试放在哪一层？会不会和别处重复？
4. 我是不是引入了抽象/依赖/目录？如果是，触发条件是什么？
5. 我能给出跑过的验证命令和输出吗？
