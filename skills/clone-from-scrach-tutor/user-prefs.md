- **代码风格（2026-10-03 用户要求）：手搓代码尽可能优雅易懂**——宁可多两个小函数也不要一段聪明但难读的代码；标识符见名知意；注释只解释"为什么"。coder/writer 交接必须携带此要求。
- **画图工具（2026-10-03 起）**：按 `skills/draw-diagram` 路由——序列图/流程图嵌 mermaid；架构图默认 fireworks-tech-graph，简单图可用 d2、调 2 轮不合格立即切 fireworks。迭代靠文本几何报告，每张图定稿时才目检一次；已有同系列图必须增量改。
- 里程碑的代码实现交由 subagent 构建，主 agent 保留设计、验收与讲解。
- **章节结构（2026-09-30 用户定调，已落 SKILL.md Phase 3 writer 约定）**：问题驱动开篇 → 通俗背景概念 → 设计（架构图/流程图先行，先于代码）→ 代码领读 → 验收 → 与原版差异 → 常见坑与展望。模板参照"网上讲得好的技术教程"。
- **里程碑切分（2026-09-30 用户反馈"M0/M1 还简单，后面越来越不 bite"；2026-10-03 补充：Bite 数量不定死，按实际情况）**：按依赖树/模块划里程碑是对的；硬性约束只有两条——一轮交互只交付一个 Bite（可独立验收的最小闭环）、里程碑大小上限（新概念≤2/模块≤5/决策卡片≤3，超出拆 Ma/Mb）。里程碑本身就是小闭环时 1 个 Bite 交付即可，不硬拆。已落 SKILL.md Phase 2/3。
- **终态对齐口径（2026-09-30 用户定调，修订铁律 8）**：功能点必须与原项目一致——reference 支持的 feature 到最后一个里程碑必须都支持（reference 自身的 bug 除外）；模块切分/抽象/架构允许自主设计，原版的架构不一定优雅，学的是算法与机制。

## 语言与用词（2026-09-29 用户反馈"用词总是太晦涩"；同日两次补充：误译问题 + 英文原词问题）用词三层规则，按优先级：
1. **用户日常已熟的英文原词直接用英文，不翻译**：SKILL、tutorial、viewer、daemon、policy、deadman 等。翻成中文（"技能"/"教程"/"查看器"）反而让用户脑内多转一道。
2. **有准确且通行中译的用中文**：状态机、总线、观测、关节。
3. **行业词没有通行中译或易歧义时**：禁止硬译（phase→"相位"是误译，状态机语境必须是"阶段/模式"）；要么换日常说法，要么首次出现用一句大白话声明（如"斜坡=让关节目标沿直线慢慢爬过去的渐变过程，词源是目标-时间曲线长得像斜坡"）。默认读者没有任何控制理论基础。
- 教程行文优先日常词与动词短句（"驾驶中"优于"Driving 阶段"、"瘫软"优于"Limp"），代码标识符保留英文原样但首次引用处给中文读法。
- 决策卡片等结构化段落每句自检"外行读这句能否复述"。
