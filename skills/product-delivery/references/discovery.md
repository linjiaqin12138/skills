# Grill 与发现（拷问）

用于 L 的阶段 A，以及任何「用户还没想清楚」时的意图闸。一次只问一个问题；用户答完后复述，确认后再问下一个。

## 规则

1. 先读已有 `product/*`、`architecture/*`、当前变更包，**已有答案的不要再问**。
2. 开放题优先；需要选型时先让用户描述，再给 2～3 个方案（含推荐与取舍），不要一上来选项套牢用户。
3. 把已确认内容写入 `design-decisions.md` 或 `product/`（宏观），并标明「已确认」。
4. 推测必须标「建议」，不得写成已确认。

## 题库（按需选用，非问卷一次性抛出）

### 价值与范围

- 做完后用户能亲手演示的成功是什么？
- 没有 UI、只靠 CLI/会话，价值机制还成立吗？
- 本期明确不验证什么？
- 最大风险假设是哪一条？如何用最小竖切打到它？

### 人机分工

- 默认谁起草内容（人 / agent）？人主要是否决、强编辑，还是填写？
- 「确认」针对整批还是单个对象？
- 失败时用户看到什么、能做什么？

### 扩展点（产品级）

- 以后若出现「同级另一条能力」，用户心智是换模板、换模块，还是换应用？
- 平台保证所有能力共用什么（审查、版本、消耗、存储）？什么必须各能力自带？
- 本期只做一条能力时，文档里要写下的**边界承诺**是什么（不是空插件代码）？

### 数据与真相源

- 逻辑状态以什么为准（单文件、多文件、DB…）？
- 谁可以写它？UI 能不能直接改？
- 历史版本保留规则？

### 成功标准

- 哪 3～5 条验收句能证明 MVP/本期变更成功？
- 什么情况算失败（产品理解错了，而不只是 bug）？

## 方案对比格式

单独一条消息给出：

```markdown
## 方案
### A（推荐）：…
- 利：
- 弊：
### B：…
### C：（可省略）
## 建议选 A，因为…
## 需要你拍板的一点：…
```

用户确认前不落设计细稿、不写码。

## 与其它 skill

- 价值路径仍是糊的：可读并遵循 **`processize`**，把「手搓步骤」变成操作清单输入。
- 画流程图/时序：用 **`draw-diagram`**，产出路径见主 SKILL「图放哪里」。
