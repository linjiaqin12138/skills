# 用户提问与解答记录

## 2026-10-03 · mini-sh 要自己写吗？现成源码不能用？要写编译器？

**问**：mini-sh 要我们自己写？有没有网上现成源码可以编译？是不是要自己写个编译器？

**答**：
1. **编译器不用写，已经有了**——rustc 就是编译器。同一条工具链既能编内核也能编用户态程序，只是编译参数不同（用户态 = x86_64 裸机 target + 我们自己的 syscall 封装库）。"自己写编译器"这个问题不存在。
2. **现成 shell（bash/dash/busybox）为什么不能拿来就编**：它们是 C 写的，站在 libc 和完整 POSIX 上。要编译它们，得先给我们的 OS 移植一个 libc（newlib/musl），而 libc 反过来要求内核先实现它依赖的全部 syscall——鸡生蛋；且"移植 libc"本身是偏离教学主线的大工程。
3. **自己写 mini-sh 不麻烦**：M12 的第一版核心就是一个循环——读一行 → 拆参数 → 内建命令或 fork+exec → wait，约 150 行 Rust。重定向/管道是 M14 的小增量。而且自己写的 shell 里每个 feature 都直接对应一个内核机制（fork、exec、pipe、信号），写它就是对内核最好的验收——shell 是内核的第一个真实用户。

## 2026-10-03 · 网上有没有现成的"手搓 shell"可以直接编译？

**答**：有，最好的候选是 **MIT xv6 的 sh.c**（教学 OS 的标准 shell，499 行）。实测它的依赖面极小：内核侧只要 11 个 syscall，库函数 7 个，加一层 ~250 行 C 的兼容 shim（翻译 open 标志位、exec 补 envp 等）就能嫁接到我们的 ABI 上。
**为什么不选它当主线**：它是 C——本项目一条主线是"顺便教会 Rust"，用户态是重要的 Rust 练手场，引入 C shell 会让这条线断档。
**它在我们项目里的角色**：① 写 mini-sh 时的**设计参照读物**（它的 parsecmd/runcmd 递归结构是 shell 实现的标准教材，读它比闭门造车强）；② M12 的可选支线——如果想体验"给 OS 嫁接现成软件"（含 shim 层设计），到时可以把 xv6 sh.c 移植作为加餐。
