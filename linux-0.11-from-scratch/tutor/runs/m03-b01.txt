===== COVERAGE GAPS (not asserted by the standard; noted for the record) =====
a) The rate is not asserted by the script. "3..8 samples in a 6 s window" plus the
   presence of jiffies=100/200/300 bounds the rate only to roughly 50-133 Hz, and
   a kernel that printed hard-coded strings (or a plain software counter) at the
   right moments would pass every current assertion. My host-clock measurement
   (99.5-99.8 Hz over 600 jiffies, two runs) is the only evidence that the LAPIC
   timer, not a fake, produces the samples.
b) The 6 s window starts at qemu launch, but jiffies=0 happens ~1.0-1.4 s later
   (limine boot + kernel init + PIT calibration), so only ~4.6 s of timer time
   exists in the window; the sample count therefore mixes boot latency with rate.
   The observed 4 samples (100..400) is consistent with 100 Hz, but the count
   alone cannot separate "slow timer" from "slow boot". A boot-time-aware
   measurement (or a fixed jiffies delta instead of a fixed host window) would be
   stricter.
c) The screendump is only checked for existence and size (> 10240 bytes); its
   content is not checked. A regression that stopped drawing to the framebuffer
   while keeping serial output would still pass. (Verified manually here via the
   PPM glyph decode.)
d) Nothing ties the counter to vector 32 / LAPIC specifically: no handler-side
   vector echo, no "IRQ32" marker, no check of the spurious vector 0xff that
   lapic.rs:139 programs. The IDT wiring is only inferable from code reading plus
   the observed 100 Hz rate.
e) EOI and "no lost tick" are proven only indirectly (jiffies advanced by exactly
   +100 at every sample, 7 samples x 3 runs). There is no assertion that an EOI
   was actually written; a missing EOI would also have stopped the IRQ stream, so
   the current evidence is strong but indirect.
f) The LAPIC MMIO mapping path is opaque from outside: impl/kernel/src/lapic.rs:144-189
   first tries the Limine HHDM and only falls back to a hand-built one-page
   mapping. Which branch was taken in this environment is not observable in the
   log, so the "narrow one-page mapping fallback" is neither exercised nor
   disproved. Likewise the legacy-PIC masking (lapic.rs:208-211) leaves no trace
   in the log.
g) Register save/restore in timer_entry (idt.rs:242-283) is only indirectly tested:
   the kernel keeps running and prints correct values afterwards. Nothing checks
   that a callee-saved register or the stack pointer survived the round trip
   intact, and no deliberate stress (e.g. an interrupt landing in the middle of
   a printk) is exercised.
h) The "M1: fb mask ..." line and the exact count of the 60 M1 scroll lines are
   not asserted by the script (only the two ends 00 and 59 are). I confirmed all
   60 lines and the mask line are present.
i) The build was incremental in these runs (cargo: "Finished dev profile in
   0.07s", no recompilation), so a from-scratch compile of the current tree was
   not exercised end-to-end here; the ISO was rebuilt every time and the ELF is
   newer than every file in impl/kernel/src.
