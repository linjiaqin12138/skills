A

问题

Bite1 能在屏幕上画固定字符串。但有三件事做不了：

  1. 打不出数字。Bite1 为了打印 FB 宽高，手写了一个 write_u64 转换函数。本 Bite 已删掉它。内核日志里全是数字：地址、寄存器、计数器。每条都手写转换不现实。
  2. 屏幕写满就没地方放。Bite1 的光标到底为止。第 38 行起的内容无处显示。800×600 屏配 8×16 字体只有约 37 行。
  3. 屏幕和串口各写一份。Bite1 里 main 先画屏再调 serial。两处内容靠程序员自觉保持一致。日志一多必然漂移。

不解决会怎样：M2 的 panic 现场报告、M3 的中断日志都建在 printk! 上。没有它，后面所有里程碑失去打印能力。

本 Bite 交付：fmt::Write 实现 + printk! 宏；双写收进一个点；触底滚屏。

B

背景卡片：fmt::Write 与 printk! 宏

【背景卡片】core::fmt::Write 与 format_args!

  • 一句话：Write 是一个"会接收文字"的接口。谁实现它，write! 格式化宏就能把文字写到谁身上。
  • 为什么没有 std 也能格式化：格式化引擎在 core 里，不靠操作系统。你只实现一个 write_str 方法。{:#06x} 这类占位符由 format_args! 在编译期展开成分段调用。运行时逐段调你的 write_str。
  • 最小示例：一个不接屏幕的 Write，把每个字节累加成 checksum。已实测：

输出：checksum=12。格式化文本的每个字节都流过了我们的 write_str。内核里把"累加"换成"画到显存 + 写串口"，就是本 Bite 的全部。

【背景卡片】macro_rules! 与 $crate：printk! 为什么是宏

  • 一句话：宏是在调用点展开成代码的模板。printk! 必须是宏，不能是函数。
  • 为什么：
    1. Rust 函数没有可变参数。printk!("{}", x) 和 printk!("{} {}", x, y) 参数个数不同，只有宏能都吃下。
    2. format_args! 的结果借用全部实参，只能在调用点就地消费。存进变量带走，借用的实参可能已销毁。实测反例：let args = { let n = 42; format_args!("{}", n) }; 编译报 E0597 n does not live long enough。
    3. $crate 让展开后的路径永远指回定义宏的 crate。在任何模块调用都能解析到 console::_print。
  • 最小示例：已实测：

输出：[K] n=0x002a。$($arg:tt)* 原样吞下所有参数，转发给 format_args!。

背景卡片：static mut 与 ptr::copy

【背景卡片】static mut 与 addr_of_mut!

  • 一句话：全局可写变量在 Rust 里是危险区。编译器拒绝让你直接给它取 &mut 引用。
  • 为什么：&mut 承诺"此刻只有我一个人在改"。全局变量谁都够得着，编译器无法验证这个承诺。内核 crate 用 edition 2024，&mut 某个static 是直接报错（lint 名 static_mut_refs）。实测反例：let r = unsafe { &mut COUNT }; 在 edition 2024 下编译失败。
  • 绕法：addr_of_mut! 拿裸指针。裸指针不做独占承诺，责任转给程序员：你在 unsafe 注释里写明为什么此刻安全。

【背景卡片】core::ptr::copy：memmove 语义

  • 一句话：一次整块拷贝，源区和目标区允许重叠。结果如同先复制到临时区再写回。
  • 为什么滚屏需要它：滚屏 = 整屏内容上移 16 个像素行。目标区（屏幕顶部）和源区（屏幕第 17 行起）必然重叠。朴素正序循环逐字节拷会读到刚写过的值，数据被污染。

E

设计：三张决策卡片

【决策卡片 1】双写点放在 Console::write_str 内部

  • 决策点：屏幕和串口两个出口，"两边都写"的逻辑放哪一层。
  • 备选：(a) printk! 宏里分别调 console 和 serial；(b) 原版 Linux 的 register_console 多控制台分发链；(c) 收进 Console::write_str（所选）。
  • 选择理由：屏幕和串口是同一个控制台的两个出口。收在一个点，两处内容永远一致，调用方完全无感。当前只有两个出口，分发链是过度设计。
  • 放弃的成本：对着 (b)——可扩展性没要到。以后加第三个出口（比如 netconsole 把日志发到网络），必须改 write_str 内部，而不是挂一个新节点。(b) 的"加出口不改调用方"这个好处我们没拿到。对着 (a)——出口独立演化的自由没要到：串口和屏幕被绑死在同一条路径上，想只打一边得另开口子。
  • 失效边界：出口大于两个，或需要运行时开关某个出口。

【决策卡片 2】全局控制台用 static mut 无锁

  • 决策点：全局唯一的控制台实例，怎么存、怎么防并发。
  • 备选：(a) spin crate 的 Mutex（no_std 可用）；(b) core::cell::UnsafeCell 自封装；(c) static mut + addr_of_mut!，无锁（所选）。
  • 选择理由：现阶段内核单核、无中断、无并发。锁是纯开销，还引入一个此刻用不到的并发概念。unsafe 注释里写明安全假设即可。
  • 放弃的成本：对着 (a)——现在就拿到中断安全没要到。选 (a) 的话 M3 引入中断后一行都不用改；我们选的是 M3 回头换锁。换来的是现在不用背并发概念。对着 (b)——类型系统强制隔离 unsafe 的好处没要到，安全靠注释和人肉。
  • 失效边界：M3 引入中断后，printk 可能在中断上下文重入。届时必须换锁或临界区。已登记偏差簿 D15。

【决策卡片 3】滚屏用 ptr::copy 整屏像素搬移

  • 决策点：光标触底时，怎么给新行腾地方。
  • 备选：(a) 文本环形缓冲 + 按需整屏重绘（终端模拟器做法）；(b) 显存硬件滚动（VGA 文本模式的 origin 寄存器技巧）；(c) ptr::copy 整屏上移 + 底行填背景（所选）。
  • 选择理由：一条 memmove 语义调用就完事，不需要额外的文本缓冲数据结构。(b) 在 framebuffer 下物理不存在——那是 VGA 文本模式寄存器的能力，线性显存没有。
  • 放弃的成本：对着 (a)——scrollback 翻页回看没要到。像素被覆盖就没了，屏幕上的历史无法找回；文本缓冲方案天然存着全部历史，随时能回看。当前调试靠串口全量日志补偿这个缺口。
  • 失效边界：需要终端回看历史时重新评估。预定 M13 tty 里程碑再议。

代码领读

按「设计」的顺序走：宏入口 → 双写点 → 滚屏触发 → 像素搬移 → 全局实例 → demo。

宏入口与后端。printk! 在调用点展开成 _print(format_args!(...))。_print 拿到全局控制台后调 write_fmt。未初始化时静默丢弃——降级路径下串口由 main 直写，见 main.rs:22、27-28。

双写点。每个字节先上屏再镜像串口，一处代码保证两处一致。这就是决策卡片 1 落的位置。

滚屏触发。newline 把光标下移一行。触底时调 scroll_up 再把光标退回最后一行。put_char 在行尾放不下一个字形时也会换行。

像素搬移。core::ptr::copy 一次调用把 [shift, total) 搬到 [0, total-shift)，重叠安全。底部腾出的区域逐像素填背景色——走 put_pixel，自动兼容 16/24/32 bpp。

全局实例。static mut CONSOLE 只在 init 里写一次。global() 经 addr_of_mut! 拿裸指针再解引用，绕开 static_mut_refs lint。两处 unsafe 注释都写明安全假设：单核、无中断、无并发。

demo。回归 marker 与 fmt 演示都走 printk!。60 行压测远超屏幕容量（600/16 ≈ 37 行），必然触发滚屏。Bite1 手写的 write_u64 已删除。

I

常见坑与展望

坑 1：rootless docker 的 chown 映射错位

chown -R $(id -u) 在容器内是错的。宿主机 uid 1000 在 rootless 容器里映射为 0；容器内 chown 1000 映射回宿主机变成 100999。结果宿主机对 build/ 彻底失去写权限。修法：chown -R --reference=/work /work/build，直接取挂载点属主，rootless 与非 rootless 都对。Makefile:62-64 有注释。

坑 2：static_mut_refs lint

edition 2024 下 &mut 某个static 直接编译失败。必须用 core::ptr::addr_of_mut! 拿裸指针再解引用。编译器的 help 会提示 &raw mut，两者等价。

坑 3：滚屏后的断言必须走串口

屏幕只有可见窗口。回归行会被滚出屏幕。任何"打印过就算数"的自动化断言都要 grep 串口日志，不能依赖屏幕内容。

展望 M2：GDT/IDT + CPU 异常接管 + panic 打印。现在的 panic_handler 只会 halt（main.rs:76-79），死得无声无息。M2 让它能用 printk! 报告异常名与寄存器现场——本 Bite 的格式化打印就是那颗子弹。同时 D15 的时钟开始计时：M3 中断一到，无锁全局控制台必须换锁。

读者提问与解答，按标注位置排序：

问 1（标注在 Checksum 示例上）：write! 是不是编译期把占位符替换好、拼出完整字符串，运行时交给 checksum 逐字节累加？

不是。编译期只做占位符的解析与类型检查：{:#06x} 语法对不对、实参有没有实现 LowerHex。替换发生在运行时。而且关键事实：完整字符串从不存在。format_args! 展开后是一台走马灯，逐段喂给你的 write_str。实测间谍实验（write_str 里打印收到的每段，宿主 rustc 1.98.1 跑通）：

输出 6 段："hex="、"0x"、"0"、"0"、"2a"、" dec=42"。连格式化好的 0x002a 都拆成前缀、两个补零、数字四段送进来。这就是 no_std 无堆也能格式化的原因：不需要分配内存存结果，字节一边产生一边流走。我们的 console 同理：字节流过 write_str 时当场画屏加写串口，屏幕上也没有"一个字符串"。注意分段数是编译器内部实现细节，会变；唯一可靠的是"逐段、无整串"。

问 2（标注在 format_args! 借用规则上）：let args = { let n = 42; format_args!("{}", n) }; 为什么 n 活得不够久？编译期不就能确认是 42 吗？

format_args! 的产物是 fmt::Arguments。里面存的不是值 42，而是指向 n 内存的引用，外加一个函数指针（用哪个 trait 格式化）。为什么存引用而不拷贝值？这套机制要服务任意类型、任意来源的值。实参可能运行时才存在，比如键盘输入的数字。编译期不存在的东西，没法在编译期拼进字符串。

所以编译器不为 format_args! 做常量折叠。玩具例子里人眼看得出是 42，但机制是通用的。通用机制只认一条：借引用，活着才能用。

块结束，n 的栈内存被回收，args 里的引用就成了悬垂指针。E0597 拦的正是这个。

生活类比：args 像一张便利贴，上面写着"答案在第三个抽屉"，而不是把答案复印了一份。便利贴很轻、可以到处传，但前提是抽屉里的东西还在；东西被扔了，便利贴就指向空气。差异点：现实里便利贴失效要等用的时候才发现；Rust 在编译期静态拦下，根本不许你把便利贴带出抽屉的生命周期。另外便利贴上还贴着"用什么格式念出来"的说明（Display/LowerHex 函数指针），这是引用之外的第二件东西。

问 3（标注在 kprint 宏示例上）：macro_rules! kprint { ($($arg:tt)*) => { ... } } 这语法怎么读？

一个宏定义就是一条"模式 → 模板"规则。读法：=> 左边是匹配器（matcher），右边是转写器（transcriber）。

  • $arg:tt：捕获一个 token 并起名 arg。tt（token tree）是 Rust 词法单元：单个标识符、字面量、符号各算一个；一对括号连同里面的全部内容算一个。
  • $( )*：括号里的模式可以重复任意次，含 0 次。$($arg:tt)* = 把调用时写的所有 token 逐个捕获下来。kprint!("n={:#06x}", n) 捕获到 3 个 token：字符串字面量 "n={:#06x}"、逗号 ,、标识符 n。
  • 右边 $($arg)*：把捕获的 token 原样吐回模板对应位置。

所以 kprint!("n={:#06x}", n); 展开后就是 println!("[K] {}", format_args!("n={:#06x}", n));。宏做的只是"按模式吞下 token、按模板吐回 token"，不理解也不检查 token 的含义；类型检查发生在展开之后。对照 kernel/src/console.rs:119-123 的真实 printk!，结构一模一样，只是转写目标从 println! 换成 $crate::console::_print(core::format_args!(...))。

问 4（标注在问 1 解答上）：format_args! 展开后是一段循环代码是吗？

接近，但循环不在你的调用点。展开分两半：调用点生成的是数据，一个 fmt::Arguments 结构体。循环在 core 库的 write_fmt 函数里，全程序只有一份。概念示意（非真实展开，真实实现有更多优化变体）：

所以问 1 间谍实验看到的 6 段，就是这台走马灯的脚印。字面片段各算一段；{:#06x} 的 LowerHex::fmt 内部又拆出前缀、两个补零、数字几段。编译期做的是"切片段、填表"；运行时是 write_fmt 的循环加各实参的格式化函数。

Arguments 这张表是所有格式化宏共享的中间格式。write!、println!、format! 只负责造表，消费表的代码只有一份。

两个自问自答的预习条目：

  • 问：为什么 fmt 演示行里 0x002a 有前导零？ 答：{:#06x} 的含义是：十六进制（x）、带 0x 前缀（#）、总宽 6 字符、不足补零（0）。42 = 0x2a，补到 6 位就是 0x002a。
  • 问：滚屏一次搬多少字节？ 答：(height - 16) * pitch。800×600×32 且 pitch 无对齐冗余时约 1.8MB。memmove 级速度，人眼无感。
