A

问题

M0 只能往 COM1 串口喊话。人眼看不见内核在「屏幕」上说了什么。

原版 Linux 0.11 早期用文本模式（约 80×25 字符）。我们走 Limine 图形路径，自己画像素。

本 Bite 要解决的事：

  1. 向 Limine 要一块线性 framebuffer。
  2. 按协议读宽高、pitch、bpp、RGB mask。
  3. 用自制 8×16 字体把固定字符串画到显存。
  4. 串口同步输出，方便自动化 grep。

不解决会怎样：后续 printk、panic、调试信息只能进串口。没有图形验收路径，也无法兑现偏差簿 D9「手搓显示端」。

本 Bite 明确不做：printk!、core::fmt::Write、滚屏。这些归 Bite2。

B

背景：线性 framebuffer

【背景卡片】线性 framebuffer

  • 概念：显存是一块按行扫描的像素数组。每个像素占固定位数（bpp）。写 (x,y) 时偏移是 y * pitch + x * (bpp/8)。
  • bpp / pitch：bpp = 每像素位数（32 → 4 字节）；pitch = 一行在内存里的实际字节数（常含对齐，大于 width×每像素字节）。
  • 为什么需要：BIOS 文本模式不再可用；我们要自己往显存填 RGB。算错偏移会花屏或写穿别的行。
  • 最小示例（Node，演示 pitch ≠ width×字节数）：

预期：pitch 32 packed 16，前 8 字节为 [0,0,0,0, 0,255,0,0]。

决策导览

本 Bite 两张决策卡片：

  1. Limine 协议绑定：手写 → 改用 limine crate（D14）。
  2. 像素颜色按 mask 打包，还是写死 x8r8g8b8。

【决策卡片】Limine 协议绑定（crate）

  • 决策点：内核如何拿到 framebuffer 请求/响应类型与魔数。
  • 备选：
    1. 按 limine.h / PROTOCOL.md 手写 #[repr(C)]（交付时曾选）
    2. bindgen 链入官方头文件
    3. 依赖现成 limine crate（现行）
  • 选择：备选 3（2026-10-13）。用户偏好「少造轮子」；官方 crate 0.6.5 提供 BaseRevision / FramebufferRequest / start·end marker，行为与手写一致。登记偏差 D14。
  • 放弃的成本：
    • 没选手写：少了「每一字节布局自己看得见」的教学透明度；换「少样板、跟上游类型」的维护成本。
    • 没选 bindgen：仍要维护 C 工具链与 build.rs；crate 已够用。
  • 失效边界：crate 与本机 Limine 协议 revision 不兼容时，需升 crate 或核对 BaseRevision。本机仍请求 revision 3（crate 最高支持 6，向下兼容）。

【决策卡片】按 mask 打包像素

  • 决策点：(r,g,b) 如何变成显存里的一个像素字。
  • 备选：
    1. 用 response 的 *_mask_size / *_mask_shift 打包（所选）
    2. 写死 x8r8g8b8（0x00RRGGBB）
  • 选择：备选 1。fb::pack_rgb 按 mask 截断再移位。串口打印 mask，便于核对。
  • 放弃的成本：
    • 没选 2（写死格式）：实现短、当前 qemu 路径几乎一眼能懂。我们放弃这份「三行写完」的简单，换对 bpp/mask 变化更稳的路径。
  • 失效边界：memory_model 不是 RGB、或 bpp 不是 16/24/32 时，put_pixel 直接丢弃。换主机/固件后务必看串口 M1: fb mask …。

可选旁注：字体自制几何点阵，未嵌 PSF。好处是无外部字库许可问题；代价是字形丑、缺字只能画实心块。Bite 范围只覆盖可打印 ASCII。

代码领读

顺序跟设计走：crate 请求 → 取 FB → 写像素 → 字形 → 控制台 → _start → 链接坑相关配置。

1. limine crate 请求与 first_framebuffer

依赖 limine = "0.6.5"。静态请求放进分段后的 .limine_requests_*，由 linker 排成 start → 请求 → end。

BaseRevision::with_revision(3) / FramebufferRequest::new() 替代手写魔数与 repr(C)。

Rust：Option<&'static Framebuffer> 表示「可能没有 FB」；? 在返回 Option 的函数里把 None 提前返回。[^option]

2. 按 mask 写像素

address() 是 crate 的访问器（字段本身私有）。

as：做数值类型转换（如 u8 → u32）。[^as] write_volatile：告诉编译器「这次写不能优化掉」，显存属于 memory-mapped I/O。

3. 点阵字形与控制台

font::glyph：可打印 ASCII（0x20..=0x7E）查表；其它字符画实心块，避免「空白像空格」。

Rust：impl Console { … } 给结构体挂方法；&mut self 表示方法会改光标。[^impl] s.bytes()：按 UTF-8 字节迭代；本 Bite 字符串全是 ASCII，一字节一字。 newline 只下移 FONT_HEIGHT，不滚屏——行数超出后由 put_pixel 静默丢弃。

4. _start：画屏 + 串口双写

mod console; 等：声明同目录模块。[^mod] const LINE_*: &str：字符串切片，存在只读数据里。 失败路径仍打印 M0: kernel alive，保住 M0 回归标记。

配置侧：limine.conf 请求 800x600x32。

链接侧：请求段顺序 + .got 进可写 .data + 关 GNU_RELRO——见「常见坑」。

脚注（Rust 语法速查）：

  • [^option]: Option<T> 表示有或无；None / Some(值) 两态。函数里 ? 遇 None 直接返回。
  • [^as]: as 是显式数值转换；截断由你负责。
  • [^impl]: impl 给结构体挂方法；常见接收者是 &self / &mut self。
  • [^mod]: mod name; 去找 name.rs 或 name/mod.rs。

常见坑（实测）

细节展开

pitch、bpp 是什么？（面板 B）

bpp = bits per pixel，一个像素用几位存颜色。本机 32 → 每像素 4 字节。

pitch = 内存里往下挪一行要加的字节数。它常大于 width × (bpp/8)，多出来是对齐填充。

公式用 y * pitch + x * (bpp/8)，不要用 y * width * 4。展开见 线性 framebuffer HTML。

8×16 是一个字符的像素块吗？（面板 C）

是。每个可打印字符对应一张 8 宽 × 16 高 的点阵（glyph）：16 行、每行 1 字节。

手写结构体 / 换成 crate？（面板 C、H）——已换成

2026-10-13 已改用官方 limine crate 0.6.5。limine_fb.rs 只保留请求静态量与 first_framebuffer() 薄封装。

make check-m1-b1 复跑通过。登记偏差 D14。偏好见 docs/user-prefs.md。

mask 是什么？（面板 C）

mask = 像素字里「哪几位是红/绿/蓝、从第几位起」的说明书。串口 r8@16 g8@8 b8@0 即此。

write_volatile 是大端还是小端？（面板 D）

跟 CPU 目标架构走。 x86_64 固定小端 = 低字节放低地址。write_volatile::<u32> 按本机端序写。

mask 是位域；端序是字节落盘顺序——两层别混。

24bpp 分支是按小端拆三字节（pixel & 0xff 先写最低地址）。

glyph 是啥？（面板 D）

glyph（字形） = 单个字符的点阵形状。draw_glyph 画它；newline 只挪光标。

RELRO / 段布局示意图（面板 D 建议）

ELF 段布局与 RELRO。

为什么字体要自制？（面板 F）

裸机图形模式无系统字库。本 Bite 自制 ASCII 点阵；后续可嵌 PSF。
