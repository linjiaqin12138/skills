A

问题

M1 的内核能打印了，但一出错就死得无声无息。这不是假设：本 Bite 的第一版 GDT 代码就跑出了这个症状。

  1. 某条指令触发 CPU 异常，比如写只读内存触发 #PF。
  2. CPU 查 IDT 找处理函数。此刻 IDT 还是 Limine 留下的，已无效。
  3. 找不到处理函数，异常升级为 double fault。它也处理不了，CPU 复位。
  4. qemu 里虚拟机重启，从头再跑，再死。串口日志反复出现 M0: kernel alive。

这就是三连重启：崩溃不留线索，连死在哪条指令都不知道。

不解决会怎样：M3 要开外部中断，M5 要做缺页，M8 要切 ring3，都会频繁触发异常。没有异常接管，后面每一步调试都只能靠猜。

本 Bite 交付：自己的 GDT + 256 项 IDT + 异常现场打印。验收动作是故意执行除零指令，预期打印异常名、出错地址、全部寄存器，然后停机，不重启。

B

背景卡片：GDT 与段描述符

【背景卡片】GDT：段寄存器指向的那张表

  • 一句话：GDT 是内存里一张表，每行 8 字节描述一个内存段。段寄存器（CS/DS 等）装的不是段，是"这张表第几行"的编号（选择子）。
  • 为什么需要它：64 位长模式下，分段的隔离功能已废弃，内存隔离归分页管。但 CPU 仍要求段寄存器指向合法描述符。代码段描述符的 L 位还负责声明"这是 64-bit 代码"。Limine 有自己的 GDT，内核要自立门户就得建自己的表。

C

背景卡片：IDT、异常与栈帧

【背景卡片】IDT：CPU 的"出事找谁"表

  • 一句话：IDT 是一张 256 行的表。CPU 出事时按向量号查表，跳到该行登记的处理函数。
  • 异常 vs 中断：异常是 CPU 执行指令时自己发现的问题，除零是向量 0，缺页是向量 14，同步发生。中断是外部设备敲门，定时器、键盘通常从向量 32 起，异步发生。两者共用一张 IDT。
  • 栈帧：CPU 跳处理函数前，自动把 rip/cs/rflags 压栈，部分向量还压一个 error code。这份栈上数据就是"现场"，处理函数靠它报告死因。
  • 最小示例：你每天都在间接用这套机制。用户态程序除零，是内核的 IDT handler 接住异常后包装成 SIGFPE 信号投递给进程。下面 C 程序注册 handler 后真除零，已实测：

D

设计：模块与数据流

两个新模块的职责边界：

  • gdt.rs：三项扁平 GDT，null + 内核代码段 + 内核数据段。lgdt 换表，然后逐个重载段寄存器完成接管。不建 TSS，那是 M8 特权级切换才需要的。
  • idt.rs：256 项 IDT。向量 0~31 装 interrupt gate，指向 32 个汇编 stub。stub 统一栈帧后跳进公共出口，公共出口把现场交给 Rust 函数 exception_handler 打印。

main 里的接线是两行调用：gdt::init() 先，idt::init() 后。顺序不能反：IDT 门描述符的 selector 字段填的是 KERNEL_CODE_SEL（idt.rs:13 从 gdt.rs 导入），这个选择子只有新 GDT 生效后才合法。serial、console、fb 等 M0/M1 模块一行未动。

E

设计：三张决策卡片

【决策卡片 1】interrupt gate 还是 trap gate

  • 决策点：IDT 门描述符的类型字段选哪种门。
  • 备选：(a) interrupt gate，进门时 CPU 自动清 IF，异常处理期间不被外部中断打断；(b) trap gate，不动 IF。
  • 选择理由：选 (a)。异常处理是脆弱窗口，现场还没打印完就被外部中断抢占，栈和输出都会乱。本 Bite 本来也没开外部中断，清 IF 是顺手加一层保险。
  • 放弃的成本：对着 (b)——不打扰 IF 状态的好处没要到。将来外部中断打开后，若 handler 需要可屏蔽中断保持嵌套响应，interrupt gate 做不到。典型场景：定时器在耗时长的 handler 里继续走。(b) 天然支持这个，我们没拿到。
  • 失效边界：M3 打开外部中断后，若出现嵌套响应需求，重新评估。

【决策卡片 2】统一栈帧布局还是两套布局

  • 决策点：有 error code 的向量由 CPU 压错误码，没有的向量不压。handler 面对的栈帧要不要统一。
  • 备选：(a) 无错误码的向量由 stub 补压一个占位 0，32 个向量一种布局；(b) 两套帧布局，handler 按向量号分叉解析。
  • 选择理由：选 (a)。一个 Rust ExceptionFrame 结构通吃全部 32 个向量，handler 不用分叉。错误码向量清单是固定的 8、10~14、17、21，由宏在生成 stub 时区分。
  • 放弃的成本：对着 (b)——省一次压栈的好处没要到。选 (b) 的话，有错误码的向量少压 8 字节，栈上少一个无意义字段。这是每个向量几百纳秒都不到的开销，换来的是 handler 按向量分叉解析现场。
  • 失效边界：没有实质失效边界。除非某天要榨干异常路径的性能，目前看不出这种需求。

【决策卡片 3】打印后 hlt 还是 iretq 返回

  • 决策点：handler 打印完现场之后，停机还是返回被打断的代码。
  • 备选：(a) 打印后 hlt 停机；(b) 恢复寄存器，iretq 返回，从犯错指令继续。
  • 选择理由：选 (a)。本 Bite 的验收只要"摔了能报告"。返回路径要弹出全部寄存器再 iretq，代码量翻倍，而除零返回去还会立刻再犯。
  • 放弃的成本：对着 (b)——从异常继续执行的能力没要到。这个能力不是可有可无的：M9 写时复制的缺页处理恰恰需要"修好页表，回去重跑那条访存指令"。到时必须补 iretq 路径，已登记偏差簿 D16。
  • 失效边界：M5 缺页、M9 写时复制到来时，(a) 必然失效，返回路径是它们的硬前提。
F

代码领读

按「设计」的顺序走：GDT 描述符 → lgdt 与段寄存器重载 → IDT 门描述符 → 栈帧结构 → 汇编 stub 与公共出口 → Rust handler → main 接线。

GDT 描述符的位拼装（gdt.rs:20-43）。两个 const fn 在编译期把标志位拼成 u64。注意 0b1011 的最低位是预置的 Accessed 位，原因见「常见坑」。const fn 是 Rust 里能在编译期求值的函数，结果是常量，直接进 .rodata。

lgdt 与段寄存器重载（gdt.rs:62-96）。lgdt 只换表，段寄存器里还是 Limine 的旧选择子，必须逐个重载。CS 不能用 mov 写，标准做法是伪造远返回帧：压新代码段选择子和下一条指令地址，retfq 顺带换 CS，执行流落回原地。options(nostack) 告诉编译器这段汇编不用栈——reload_segment_registers 里那条则明确自己压栈弹栈。

IDT 门描述符（idt.rs:34-62）。#[repr(C, packed)] 让结构体按 SDM 规定的 16 字节布局落内存，字段间无对齐填充。interrupt_gate 把 handler 的 64 位地址拆成三段塞进 offset_low/mid/high。type_attrs 里的 0b1110 就是决策卡片 1 选的 interrupt gate。

栈帧结构（idt.rs:64-90）。ExceptionFrame 的字段顺序与压栈顺序互为镜像：最后压的 r15 地址最低，排第一个字段。改任何一边都必须同步另一边，注释里写死了这条纪律。static mut IDT 用 addr_of_mut! 取裸指针操作，这套写法在 M1 Bite2 讲透，这里不重复。

公共出口（idt.rs:128-160）。#[unsafe(naked)] 加 naked_asm! 表示这个函数体整段是手写汇编，编译器不生成序言和尾声——序言会动 rsp，破坏刚压好的帧。压完 15 个寄存器后 mov rdi, rsp 把帧指针作为第一个参数传给 Rust handler。and rsp, -16 把栈对齐到 16 字节，因为 Rust 代码可能用 SSE 指令，SSE 要求栈对齐。

宏生成 stub（idt.rs:162-187）。macro_rules! 按"有没有 error code"生成两种 stub：没有的向量先 push 0 占位，这是决策卡片 2 的统一布局。stub 用 jmp 而不是 call 进公共出口，栈顶因此保持 stub 留下的向量号。宏机制本身在 M1 Bite2 讲过。

批量定义与安装（idt.rs:189-204）。define_exceptions! 一张表列出 32 个向量各自的名字与错误码有无，一次展开成 32 个 stub 加一个安装函数。向量号与 EXCEPTION_NAMES 的索引一一对应。

Rust handler（idt.rs:264-302）。打印格式就是 Makefile 验收断言的依据，改格式必须同步 check-m2-b1。再看 idt.rs:270 如何反推 rsp：同特权级异常时 CPU 不自动保存 rsp。CPU 压 rip/cs/rflags 之前的栈顶，恰好是 rip 字段上方三个 u64 的末尾。打印完 hlt 停机。interrupt gate 进门时已清 IF，hlt 不会被可屏蔽中断唤醒。

main 接线与触发（main.rs:52-77）。两行 init 之后，trigger_divide_error 用内联汇编的 div 真触发 #DE。为什么不能写 Rust 的 0 / 0：编译器给除法插了除零检查，除零只走 panic!，不进 IDT。这个伏笔指向 Bite2 的 panic 打印。

与原版差异

原版 Linux 0.11 的异常处理在 traps.c 与汇编入口里：汇编入口负责压栈，转到 C 函数打印寄存器后进入死循环。【合理推断：本地 reference/ 只有 limine 与 limine-protocol，0.11 源码不在本地，此处按公开版本的结构概述，未逐行核对文件内容】

维度 Linux 0.11 本项目
入口层 汇编压栈后转 C #[unsafe(naked)] + naked_asm!，同样汇编写入口
栈帧 各入口分别压栈 32 个 stub 统一布局，一个 ExceptionFrame 通吃
现场打印 C 函数打印后死循环 Rust exception_handler + printk!，屏幕串口双写
出错结局 死循环 hlt 停机，IF 已清不会被唤醒

偏差簿联动：

  • 新登记 D16：IDT 向量 32~255 是空洞（P=0），handler 没有 iretq 返回路径。预定收敛点：M3 装外部中断 handler、M9 写时复制的缺页需要 iretq。
  • D15 口径确认：M2 只接同步 CPU 异常，interrupt gate 进门自动清 IF，无外部中断。static mut 无锁 console 的假设仍成立，收敛点保持 M3。
  • 本 Bite 未收敛任何旧偏差。

常见坑与展望

坑 1：GDT 描述符的 Accessed 位会引爆三连重启
  • 症状：首版代码连 M2: gdt ok 都没打印，qemu 反复重启。
  • 机制：CPU 每次装载段寄存器，都会把内存中对应描述符的 A 位置 1（SDM Vol.3 3.4.5.1）。这是 CPU 对内存的隐式写。static GDT 在只读 .rodata，A 位初始为 0。这次回写触发 #PF。此刻 Limine 的 IDT 已无效，#PF 连锁升级 #DF、triple fault，CPU 复位。
  • 定位：qemu -d int 抓异常日志，发现 #PF 的 CR2 = GDTR.base+0x14，正好落在 GDT 表内部。
  • 修法：建表时预置 A=1（gdt.rs:45-47 的注释写明这条）。CPU 发现位已是 1，无需回写。描述符 type 因此用 0b1011，不用教科书上常见的 0b1010。

坑 2：Rust 的 1/0 不会触发 #DE。编译器给整数除法插了除零检查，除零走 panic! 路径，根本到不了 IDT。验收必须用 asm! 的 div 指令真触发（main.rs:66-77）。反过来想：异常接管完成了，panic! 路径还是个黑洞——这正是 Bite2 要解决的问题。

展望：

  • Bite2（下一篇）：panic 打印。给 #[panic_handler] 接上 printk!，让 Rust 层的崩溃也能报出文件、行号、信息。
  • M3：外部中断。填上向量 32 起的 IDT 空洞（D16），重新评估 interrupt gate 选择，static mut console 换锁（D15）。
  • M9：写时复制。缺页 handler 修好页表后要 iretq 回去重跑指令，返回路径到时补（D16）。
