A

问题

Bite 6 留下两个悬案。一是起身交接：坐姿起身结束交给 velstand 时，身体还停在接不住的姿态。二是行走不动点：鸭子收到前进命令原地不动，vx=0.15 走 10s 只前移约 0.005 m，只前倾不迈步。

不解决会怎样：M8 无法结案。起身接不住，sit 与 roulade 物理验收过不了。行走卡死又分不清两种可能：我们移植出了错，还是上游权重本来如此。这两种可能指向完全不同的下一步——前者继续修栈，后者指向 M9 自训策略。

本 Bite 做两个动作加一个实验。动作一：BAM 路径的步进时机从「read 时步进」改为「write 本拍先写目标再步进」。动作二：行走验收改 vx=0.8 × 10s 断言前移不小于 2.0 m（2026-10-14 用户裁决）。实验：官方与我们双侧对照，坐实行走不动点的根因。

证据链（同一权重、同一场景、同一 BAM，唯一变量是命令大小）：

实验 官方 infer_policy 我们 读法
vx=0.15 / 0.3（训练分布内） dx≈0.005 m/10s，只前倾 相同 权重对小命令不响应，双侧一致
给初速度（官方按 P 注 1 m/s；我们 Ctrl+拖拽） 步态被带起 相同 权重能维持步态，不能从静止起步

起身交接：write 先写目标再步进

这里原稿写错了机制，读者用推导加回退实验推翻了它（2026-10-14）。曾以为：旧拍序在 read 时步进，物理吃上一拍目标，交接时身体停在接不住的姿态。实际上两种拍序的递推式完全相同——都是 X(n+1) = step(X(n), f(X(n)))：旧拍序 read 先步进再回传感，下一拍 write 的目标再下一拍 read 才被消费；新拍序 read 只回传感，本拍 write 的目标本拍步进。化简后状态序列逐拍相同。实验证实：把代码临时改回读时步进，四项验收（含坐姿起身 z=0.1160、行走前移 4.93m）同样全绿。

那 Bite 7 的起身失败怎么解释？两种拍序的真实差别只在边界，示意如图（见「细节展开」）。启动第一拍，旧顺序先用初始抱持目标空走 20ms——daemon 的第一个观测落后一拍。这点的相位差经接触动力学混沌放大，足以翻转一个临界动作的成败。那次失败更可能是运气，不是机制。

保留 write 步进的真正理由：① 与官方 infer_policy.py 主循环逐拍同序（观测 → 推理 → 写目标 → 步进，:1683-1684、:1770-1777）；② read 无副作用，只读客户端怎么轮询都不会推着物理走；③ 缺 write 的拍物理冻结，而不是拿旧目标继续漂移。新拍序：

【决策卡片】BAM 步进时机：write 先写目标再步进

  • 决策点：BAM 路径的 mj_step 放在 read 还是 write。
  • 备选：
    1. write 本拍先写 q_target，再 update + mj_step（所选）
    2. read 时步进（M4 遗留拍序，非 BAM 路径仍在用）
    3. 装回 Bite 6 的冻结 + push + nudge 补偿（用户裁决禁止）
  • 选择理由：两种拍序的轨迹等价（回退实验证实），所以理由不在行为，而在工程性质与对齐——与官方 infer_policy.py 主循环同序；read 无副作用；缺 write 时物理冻结而非漂移。备选 3 已被裁决排除。

细节展开

Q：--new-cmd-obs / --action-scale 0.9 是干什么的？

action_scale 是策略输出的无量纲位置增量的幅度系数：target = default_pose + action × action_scale（infer_policy.py:875）。0.9 对齐官方运行时 robotd 的默认值（upstream/robotd/src/control.rs:69）。训练侧当前 cfg 写 1.0，部署契约以 robotd 为准【合理推断】。

--new-cmd-obs 选观测布局。legacy：48 维本体感觉加 3 维 twist，共 51D，头偏移绕过策略直接加在 ctrl（infer_policy.py:880-882）。new：48 维加 13D 命令块 [twist(3), head_pose(4), body_pose(6)]，共 61D，头与身体命令喂进策略自己协调（infer_policy.py:474-494）。

当前 velstand / sitstand / kick / roulade 都是 61D 新布局，不带开关加载会直接报错（infer_policy.py:1237-1240）。新布局下「坐下」是往 twist 的 vx 槽写 1.0（posture flag，infer_policy.py:485-489），喂全零等于「站立」。

Q：官方窗口按 ↑ 只微微前倾不动，按 P 就动起来了，为什么？

P 是手动把躯干速度设成 1 m/s，不是策略响应。这个现象说明权重能维持步态，但不能从静止响应训练分布内的小命令。后来的 0.8 实验坐实了这个结论，见「问题」一节的证据链。

Q：怎么把 ↑ 从 0.3 改成 0.8？

↑ 不是累加，按下直接 set_vel_cmd(vel_max_x)（infer_policy.py:1501）。行走模式上限在 infer_policy.py:1369，用 sed 一行改 0.8。步骤写在 tutor/verify-official-walk.md。警告：0.3 是训练见过的最大命令，0.8 是分布外输入。

Q：为什么是「write 时步进」？仿真和控制不应该各自独立演进、传感器读到什么就是什么吗？写一下动一下？

仿真从来没有自己的时钟。从 M4 起 duck_body.py 就是请求驱动的服务器。daemon 每 20ms 发一拍请求，物理才走 20ms（4 子步 × 5ms）。daemon 不连，物理就冻结。

让仿真按墙钟自由跑，等于把物理绑到 CPU 速度上。那样没法单拍暂停调试，结果也不可复现，「前移 ≥2.0m」这类断言会失去意义。训练侧和官方 infer_policy.py 用同样的 lockstep 节拍。

本 Bite 只改每一拍内部的顺序。旧顺序在 read 时先推进物理，物理吃上一拍写下的目标，命令延迟 20ms。新顺序 read 只回传感，读到的仍是真实当前状态——「读到什么就是什么」没变。决策后写入本拍目标再立刻步进，命令延迟 0。

订正（2026-10-14）：本条原稿的机制解释错误。起身能过曾被归因于「物理不再吃上一拍目标」。下一条问答的推导加回退实验推翻了它：两种顺序化简是同一递推，读时步进四项验收同样全绿。保留 write 步进的真正理由不变：与官方蓝图主循环同序（观测、推理、写目标、步进，infer_policy.py:1683-1684、:1770-1777），外加 read 无副作用、缺 write 时物理冻结。非 BAM 诊断路径仍是读时步进（M4 遗留，见偏差簿 D68）。

Q：两种顺序不是一样的吗？旧的读之前步进，读的是写命令作用 20ms 后的影响；新的写时步进，下次读到的也是写命令作用 20ms 后的影响。不同在哪，画图示意。

推导成立，两种顺序化简后是同一个递推：X(n+1) = step(X(n), f(X(n)))。旧顺序 read 先步进再回传感，本拍 write 的目标下一拍 read 才被消费。新顺序 read 只回传感，本拍 write 的目标本拍步进。状态序列逐拍相同，命令序列也相同。

实验证实（2026-10-14）：把 duck_body.py 临时改回读时步进，四项验收全绿——坐姿起身 z=0.1160，行走前移 4.929 m。恢复 write 步进后复跑也全绿（4.862 m）。

真正的差别只在三个边界：① 启动第一拍，旧顺序先用初始抱持目标空走 20ms，daemon 的第一个观测落后一拍；② read 失败或缺 write 的拍，旧顺序物理拿旧目标继续走，新顺序物理冻结；③ 旧顺序的 read 有副作用，多一个只读客户端物理就被推着多走，新顺序 read 是纯查询。

教训记录在案：本 Bite 原稿把起身能过归因于「物理不再吃上一拍目标」，机制解释错误，「设计」一节已订正。Bite 7 那次起身失败更可能是启动相位差被接触动力学放大，是临界动作的运气。保留 write 步进的真正理由：与官方 infer_policy.py 主循环同序，外加上面②③两条工程性质。
