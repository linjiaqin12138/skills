A

问题

M7 交出了迷你 updaterd：apply 走七阶段流水线（Verifying → Extracting → arm pending → kill/swap/spawn → HealthGate → Committing/RollingBack），崩溃恢复靠 boot counter 兜底。Bite 1/2/3 已经把 daemon 的请求面收敛到原版形态——robot.move 通知式、robot.enable {on, toggle}、robot.subscribe + SubscribeResult（详见 第 9/10/11 章）。但 预检面还差两块，原版 daemon 暴露两个 RPC 给 updater 做"动手前体检"：

  • robot.safeToRestart：机器人当前能否被打断。"走路时被换"会丢姿态控制：动能在飞，重启瞬间扭矩掉，机器人往前栽。这是机器人领域有名的失败模式。
  • robot.modelApi：模型 I/O 契约版本号。updater 用它核对"新版 daemon 的策略槽位和当前策略文件还匹不匹配"。不一致时跑起来崩，崩在控制循环里更糟。

本 Bite 把这两块补齐，并接进 apply 流程。这是 M8 C1 接口对齐的第四个、也是最后一个 Bite。本 Bite 收口后转入 C2：把 BAM 移植到执行器层，让 sit/roulade 在仿真里物理站得起来。

没接的后果：

  • updater 在任何时刻都可能试图重启正在 Driving 的机器人，把本可以避免的"机器人往前栽"做成本质事故。
  • 模型契约对不上时，新版 daemon 起不来——策略输入张量形状变了，健康门超时回滚，旧版再上来。用户看到的是"为什么我刚升级完就回滚了"，而不是"模型槽变了，规则要换"。

不解决这两件事，C1 没真正收口。

B

背景概念

【背景卡片】预检 / preflight

  • 一句话：执行破坏性操作（重启、换版本）之前，最便宜的一道询问——"现在打断你安不安全"。答 yes 才动手，答 no 就退。失败零成本：跑在最前面时拒绝，连磁盘都没碰过。
  • 为什么需要它：apply 的失败点有三类——验证拒绝（manifest 对不上）、门否决（健康不过）、崩在中间（kill -9、OOM）。前两类本来就是"回滚或拒绝"的预期路径，第三类由 boot counter + 崩溃恢复收拾。但第四类是"压根不该动手"：走路时被换、版本契约不一致。预检把这第四类提前到不动手的阶段处理。
  • 最小示例：

预检的关键不在 RPC 本身（两条 JSON-RPC，几毫秒），在它位于哪个阶段——放在 apply 之前，拒绝时没碰过磁盘；放在解包之后，磁盘上已经写了一份 release，半成品清理又是新的一段逻辑。本 Bite 的第一条决策卡片就讲这个。

决策导览

本 Bite 两张决策卡片，各回答一个问题：

  • 预检放在 apply 的哪一步——选最前面，让拒绝零副作用。
  • 不可达放行、不可读拒绝——区分可达性的设计权衡。

【决策卡片】预检放在 apply 的最前面

  • 决策点：robot 预检（safeToRestart + modelApi）应当插在 apply 流水线的哪一步。
  • 备选：
    1. 放在 let from = store::current_version(...) 之后、set_phase(Phase::Verifying) 之前（所选）
    2. 放在 Extracting（解包 staging）之后、arm pending 之前
    3. 放在 spawn 新 daemon 之后、HealthGate 之前
  • 选择：备选 1。原版把 preflight 定义成 apply 的"第 0 步"——早于 manifest 校验、早于下载解包（reference/updater/src/engine.rs:662-667）。原版的理由是：预检拒绝不应该留下任何持久副作用。
  • 放弃的成本：
    • 没选 2（解包之后）：它把 manifest 校验、解包、预检串成同一段工序，失败原因落在同一阶段里查。我们拆成一步，放弃的就是这份"一道工序"的紧密度。apply 失败现在要先分辨是"预检拒的"还是"解包拒的"，日志是两行而不是一段。
    • 没选 3（spawn 之后）：新 daemon 刚起必然静止，所以这道检查永远不拒——等于白送了一次 sanity check。我们把它提到最前，放弃了这免费的确认。
  • 失效边界：预检依赖 daemon_sock（默认 /tmp/miniduckd.sock）。daemon 不在时 safeToRestart 走 Unreachable 放行、modelApi 走兜底分支被拒（验收脚本注释里把这条边界测死了——见「常见坑」1）。若 miniduckd 完全没起来（socket 文件不存在），apply 仍能继续到 Verifying；这条边界不归本 Bite 管，归 M7 的 boot counter + 崩溃恢复。

【决策卡片】不可达放行、不可读拒绝

  • 决策点：safeToRestart RPC 拿不到合法 safe: bool 应答时，怎么归类。
  • 备选：
    1. 不可达（连不上 / 超时）放行；不可读（应答形状错）拒绝（所选）
    2. 全部归 "No" 拒绝
    3. 全部放行（信任 daemon 沉默 = 同意）
  • 选择：备选 1。术语归一：Yes / No(reason) / Incompatible(reason) / Unreachable。permits_restart() 把 No 和 Incompatible 当拒绝，Yes 和 Unreachable 当放行。
  • 放弃的成本：
    • 没选 2（统一拒绝）：一条规则走天下——"没拿到肯定答复就不动手"，不必解释沉默与不可读的区别。我们放弃了这份简单，换来的是多一个变体、多一处要论证的地方。
    • 没选 3（统一放行）：任何情况都不拦，daemon 挂了也能更新——而那恰恰是最需要更新的场景；而且永远不会出现"因为字段对不上所以拒绝"这种运维看不懂的失败。我们没要到的就是这份干脆。
  • 失效边界：modelApi 的归类与 safeToRestart 不对称——它走的是另一条规则：应答形状错（None）走兜底分支被拒（model api mismatch: expected 2, got None）。safeToRestart 关注"daemon 现在是不是活的"，modelApi 关注"协议版本能不能对上"，这是两条不同的判定轴。详见「与原版差异」偏差 1。

代码领读

新增：updater 视角的 robotd 客户端

src/updater/robot.rs 是 apply 预检的全部代码——160 行，含 5 个单测。两类 RPC（safeToRestart / modelApi）共用一个 ask()：

ask() 是个"问一次、给结果或给 None"的薄壳：连不上、解析错、超时——任何环节失败都给 None。超时硬编码为 ROBOT_RPC_TIMEOUT = Duration::from_secs(1)（robot.rs:12）——预检是同步阻塞等几毫秒的活，1 秒富余。

四态判决在 safe_to_restart()（robot.rs:63-74）：

safe_to_restart 关心的是应答能否解析成 SafeToRestartResult：Ok(answer) if answer.safe → Yes；Ok 但 safe=false → No(reason)；解析失败 → Incompatible（应答是别的形状）。model_api 只问"应答能否解析成数字"——任何一步错都给 None，让上游的相等判断兜底拒绝。

SafeToRestart::permits_restart()（robot.rs:22-26）一行：!matches!(self, No(_) | Incompatible(_))。Yes 和 Unreachable 都返回 true。决策卡片 (b) 的"不可达放行、不可读拒绝"就是这两个分支的字面。

五个单测（robot.rs:117-159）覆盖所有分支：safe_true_means_yes（合法 → Yes）、safe_false_with_reason_means_no（带 reason → No）、missing_safe_field_is_incompatible（缺 safe → Incompatible 且 !permits_restart()）、unreachable_socket_is_unreachable（socket 不存在 + 100ms 超时 → Unreachable 且 permits_restart() 放行）、model_api_returns_value（Some(2)）。canned_server（robot.rs:96-115）是测试自己的 mini robotd：临时 socket 绑一个 listener，spawn 一个 task 等连接、读请求、回一份预设 JSON——把 daemon 那套协议裁到最小。

  1. 只起 updaterd、不起 miniduckd 时 apply 的真实行为（subagent 实测，主 agent 未复验）。safeToRestart 的 Unreachable 放行，但 model_api 返回 None 走到兜底分支被拒：

细节展开

预检的位置：写代码时的复核记录

coder 初版把预检放在 Extracting（解包 staging）之后，代码注释却写"拒绝没有任何持久副作用"。但解包已经把 release 写进磁盘了，注释不成立。主 agent 对照原版（reference/updater/src/engine.rs:662-667，原版 preflight 是 apply 的第 0 步，早于 manifest 校验、早于下载解包）后要求前移。

现在预检位于 let from = store::current_version(&self.paths); 之后、set_phase(Phase::Verifying) 之前（engine.rs:250-271），纯位置的挪动。

语义、文案、Phase 切换、reject 路径全部未变。accept-m8.sh / accept-m8-updater.sh 一条断言都没改仍然全绿。这条挪动对外行为没影响，但内里的不变量（"预检拒绝不留持久副作用"）是真的了。
