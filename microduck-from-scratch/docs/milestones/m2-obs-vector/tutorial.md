# 第 3 章 · M2：61 维观测向量

> 本章对应里程碑 M2（Bite 3，已验收）。交付物：`src/obs.rs`，以及 `src/control.rs` / `src/main.rs` 把向量送进 `robot.state`。

## 1. 动机

M1 的控制循环每拍能读到传感器，但读到的是结构体：关节角、速度、IMU 各有字段名。策略网络没有字段名。它在训练时吃的是一条 61 维的 `f32`，第 n 格永远是同一种物理量。

这一章在依赖树上卡在 M1 和 M3 之间：原材料是 `Sensors`，产品是 M3 要喂给 ONNX 的那条数组。现在还没有网络，所以验收不看机器人会不会走，只看这条数组的每一块落在约定的下标上。

## 2. 概念铺垫

### 【背景卡片】观测向量

- **一句话定义**：观测向量是策略的唯一输入，一条定长小数数组。下标就是协议，写错不会报错。
- **为什么需要**：网络是按训练时的列顺序学的。部署时把「关节速度」填进「上一拍动作」那一列，前向计算照样返回 14 个数，看起来像一次成功的推理。
- **和 TS 的差异**：对象多一个拼错的 key，类型检查会拦。`number[]` 多写一位，类型仍是 `number[]`。这里更像后者。另外训练分布是统计约束，不是 JSON Schema：数值合法，含义可以完全错。
- **最小示例**：`node examples/obs_layout.mjs`。跳过嘴时，偏离 home 的 0.25 在第 7 格，嘴的 1.0 不出现。不跳过时，1.0 占据下一格。实测：

```text
跳过嘴，前 8 维: 0,0,0,0,0,-1,0.25,0
位置块是否含 1.0（嘴）: false
不跳过嘴，下标 9 起: 1,0,0
跳过嘴，下标 9 起: 0,0,0
```

卡片看不懂就先读 [观测向量](../../concepts/observation-vector.md)。

布局（和原版 `duck-control` 的表一致，实现是手写的命名偏移，不是把原文件抄过来）：

| 下标 | 宽度 | 内容 |
|---|---|---|
| 0..3 | 3 | 陀螺仪，躯干系，rad/s |
| 3..6 | 3 | 重力方向，躯干系，单位向量 |
| 6..20 | 14 | 关节角减 home，不含嘴 |
| 20..34 | 14 | 关节速度，不含嘴 |
| 34..48 | 14 | 上一拍动作，策略原始输出 |
| 48..61 | 13 | 命令，见下 |

命令块：`vx,vy,vyaw`（48..51），四个头关节（51..55），然后 body x、y 恒为 0（55..57），body z、roll、pitch（57..60），body yaw 恒为 0（60）。顺序是 z、roll、pitch。每个数拉动时机身怎么动，打开 [命令量示意](../../concepts/assets/command-motion/index.html)。

### 【决策卡片】关节角先减 home

- **决策点**：位置块填绝对角，还是填「当前角 − home」。
- **备选**：绝对角；相对 home；相对上一拍。
- **选择**：相对 home。策略训练时见过的是偏离待命姿态的量，站在 home 上这 14 格应该是 0。
- **放弃的成本**：调用方若拿这 14 格去当总线目标，会得到「躺平」而不是站立。绝对角仍在 `robot.state` 的 `positions` 里。
- **失效边界**：换一套不是围绕这组 home 训练的权重，减 home 就变成错误的常数偏移。M3 装权重时，home 必须和训练配置是同一组数。

### 【决策卡片】body 的 x、y、yaw 恒写 0

- **决策点**：命令块有 6 个机身槽，客户端只表达了 z、roll、pitch。多出来的三格填什么。
- **备选**：省略这三格，把向量改成 58 维；填 0；填测到的真实机身位置。
- **选择**：填 0，宽度保持 61。原版注释写明这三轴在训练环境里没有绑定，全 0 才是正常编码，不是占位。
- **放弃的成本**：以后即使有人测到了机身 x，也不能塞进这三格，除非重新训练。
- **失效边界**：新权重如果真的把 body x 训进了观测，再写 0 就是在对网络撒谎。那时候要改的是布局契约，不是把测到的值填进去凑数。

## 3. 实现走读

`joint_of`（`src/obs.rs:51`）是嘴的唯一映射：策略槽小于 9 时关节下标相同，大于等于 9 时关节下标加 1。位置、速度、home 的抽取和 `scatter_action`（`src/obs.rs:124`）都调用它。两套映射会让嘴后面的关节集体错一格，而且类型系统看不出来。

`build`（`src/obs.rs:75`）按命名常量往 `[f32; 61]` 里填。位置块是「策略关节 − home 的策略关节」（`src/obs.rs:90-94`），不是绝对角。`last_action` 已经是 `f32`，直接拷贝（`src/obs.rs:102`）。body x/y 和 yaw 不读调用方，字面量写 0（`src/obs.rs:111-117`）。`BodyPose` 上根本没有 x/y/yaw 字段（`src/obs.rs:42`），避免有人以为传了就会生效。

控制循环在 read 成功后调用 `build`（`src/control.rs:129`）。这一章没有策略，所以上一拍动作是全 0，命令是 `Command::default()`。不在循环里留一个永不写入的 `last_action` 变量：那样读代码的人会以为动作已经在闭环里。电机目标仍走 M1 的 `ramp_target`。

快照经 watch 送到 RPC。`robot.state` 在原有 `tick` 和 `positions` 之外加上 `imu` 和 `obs`（`src/main.rs:128`、`src/main.rs:133`），频率仍是 1 Hz。读失败时不发新快照（`src/control.rs:113-122`）：本拍没有样本，watch 里留着上一帧成功的数据，订阅端会重复那一帧，而不是收到一帧空观测。

## 4. 验收

```bash
docker compose exec rust cargo test
```

11 passed，0 failed。和布局直接相关的五条：宽度之和为 61；用一组互不相同的数钉住每个块的起点；站在 home 上位置块约为 0；只动嘴，位置块不变；`scatter_action` 让嘴保持 0，下标 10 的关节拿到策略的第 10 个数。

接线：

```bash
./target/debug/miniduckd &
sleep 3
timeout 2 ./target/debug/mini-duckctl subscribe
pkill -x miniduckd
```

tick=200 那一帧的 `obs` 长度 61。下标 0..2 是 0（陀螺仪），下标 3..5 是 `0,0,-1`（重力），下标 6..19 是 0（已经站在 home，相对角为 0）。`positions` 是 home 的绝对角。这一帧里大量的 0 不能单独证明布局——速度、上一拍动作、命令在 FakeIo 上本来就是 0，块与块对调也看不出来。互不相同的那组数在单测里，不在这条订阅帧里。

## 5. 与原版差异

| 项 | 现在 | 收敛 |
|---|---|---|
| D14 | `imu` 已进 `robot.state`，推送仍 1 Hz | M5 对齐 50 Hz |
| D17 | `last_action` 恒为 0 | M3 写入策略输出 |
| D18 | 命令恒为默认零 | M4 接入速度命令 |
| 电机 | 仍是插值，不用 `scatter_action` | M3 |

行为上对齐的部分：61 维切分、减 home、嘴不进观测、body x/y/yaw 恒 0、body 顺序是 z/roll/pitch。原版用 `split_first_chunk_mut` 让每块宽度进类型系统；这里用命名偏移加单测。向量内容相同，不单列偏差。

## 6. 常见坑

1. 订阅帧几乎全是 0。站在 home、没有速度命令、没有上一拍动作时，非零的只有重力的 -1。用这一帧判断「速度块是不是写进了位置块」会得到假的通过。
2. 减 home 和绝对角要同时存在。`obs[6..20]` 是相对量，`positions` 才是总线角。拿观测去当 `write` 的目标，机器人会倒向零位。
3. JSON 会把 `0.4530` 印成 `0.453`。和 `DEFAULT_POSITION` 比的时候先按数值比，不要比字符串。
