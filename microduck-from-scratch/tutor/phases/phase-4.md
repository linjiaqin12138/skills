## 二、原作者核心决策的失效边界

逐条复盘：约束变化到什么程度，就该推翻这个决策。

1. **"进程启动绝不移动机器人"**（held_pose 抱住启动姿态、绝不 set_torque）。赌注：舵机 RAM 的 torque/目标跨进程存活，硬件状态不归进程所有。失效边界：换执行器协议（状态不再跨进程存活）或部署模型变成"进程即权威"（每次启动物理复位）时，抱住旧姿态反而危险。这条与第 5 条是同一枚硬币的两面。
2. **活着报病优于退出**（策略加载失败不退出，health 报病让 updater 回滚）。赌注：存在运维闭环（Restart=always + updater）。失效边界：没有回滚机制的开发场景里，退出+重启反而更快暴露问题；crashloop 恐惧只属于 fleet 语境。
3. **通知式连续意图**（move/head/mouth 无应答、last-writer-wins、deadman 500ms 兜底）。赌注：客户端会高频重发（padd 20–50Hz），单帧丢失无所谓。失效边界：客户端不重发时——我们自己的 CLI 就被迫扮演手柄每 100ms 重发；低频关键指令（enable/do）必须请求式，频次 × 重要性是语义选择的分界线。
4. **fallen 不 gate 任何事**（"a skill on a fallen robot is the human's call"——拒绝一个跌倒机器人的技能，就是让它永远做不了那个能扶起它的动作）。赌注：人类在场、为后果负责。失效边界：自主运行无人在场时假设不成立——这正是 FallPredictor/limp_fall 存在的语境张力；注意原版 limp_fall 默认 OFF，哲学是自洽的：默认信任人类，预测性保护是显式选项。
5. **updater 不可达放行**（safeToRestart Unreachable→permit、model_api None→兼容）。赌注：控制循环没跑就没什么会动，不可达的机器人恰恰是需要更新的机器人。失效边界：依赖第 1 条的硬件状态假设——如果 daemon 死了但电机仍带电抱持，"没什么会动"就只是近似真。
6. **协议 crate 依赖洁癖**（duck-ipc-proto 只许 serde/serde_json/semver）。赌注：协议面的稳定性与可移植性比逻辑内聚更值钱。失效边界：协议需要内嵌校验逻辑时（如我们的 finite_twist），约束迫使逻辑外流到 daemon——原版认为值，因为协议 crate 被 5+ 个进程共享，脆弱性传染面最大。
7. **BAM 解析式执行器模型**（16 标量解析式，非学习型）。赌注：舵机动力学可解析建模，仿真-真实gap 靠模型正确性而非容量。失效边界：换舵机必须重新标定（用户 M10 自研硬件路线必然触发）；出现柔性结构/高阶动力学时 16 标量不够。
8. **COAST 滑行窗与错误计数分账**（≤3 拍用上一样本续跑对策略不可见，consecutive_errors 每次失败照计喂 health）。赌注：观测本来就旧一拍，60ms 内的重投让管线平滑，比每拍分层报错更值；可见性与健康判定是两本账。失效边界：总线抖动超窗口、或 3 拍内传感器偏差已足以伤人——那时需要的不
是滑行是预测（回到第 4 条的 FallPredictor）。

## 三、可迁移原则（配迁移场景）

1. **状态所有权先于状态机设计**：先问"这份状态归谁、活多久、跨不跨进程/重启"，再画状态机。迁移场景：任何与外部有状态实体打交道的服务——打印机驱动（纸盒状态在机身）、支付终端（交易锁在机具）、浏览器自动化（登录态在 profile）。
2. **健康 = 可观测 + 可恢复，不报病比崩溃更危险**：auto-restart 体系里进程退出 = crashloop，活着把病报到能触发回滚的地方才是韧性。迁移场景：任何 supervisor/编排体系（k8s liveness 只答生死不管"为什么病"是不够的——要有 reason 面）。
3. **频次 × 重要性决定请求/通知语义**：高频低价值帧用通知 + 兜底超时，低频关键指令用请求 + 应答。迁移场景：游戏输入流、无人机遥测、实时行情推送的 API 设计。
4. **范围宪法：收敛验收走清单打勾，不靠记忆**：功能清单逐项带证据（文件:行号），验收 = 打勾而不是重新侦察；发现清单外缺口 = 流程失败。迁移场景：任何"对齐上游/竞品"的复刻、迁移、合规审计项目。
5. **删代码前查契约面，不查调用面**（D20 反转的教训）：一个分支"现在没人走"可能是上游公开契约的一部分；统计"没人在用"只能证明覆盖缺口，不能证明契约不存在。迁移场景：清理任何 SDK/协议实现/插件系统的"死代码"时。
